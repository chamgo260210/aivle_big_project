## A-2. 비동기 실행 모델 — 왜 3단으로 쪼갰나

모든 AI 실행은 `TaskRun` / `TaskAttempt` / `TaskResult` 3단을 지난다.

| 엔티티 | 역할 | 상태 수 |
|---|---|---|
| `TaskRun` | **명령 1건의 정체성.** 입력 스냅샷 · 해시 · 멱등키 · 최대 시도 수 | 8 |
| `TaskAttempt` | **한 번의 실행 시도.** claim token · lease · heartbeat · deadline | 8 |
| `TaskResult` | **산출물 1건과 채택 여부** | 4 (`RECEIVED→VALIDATED→ADOPTED` / `REJECTED`) |

쪼갠 이유는 **「같은 명령」과 「몇 번째 시도」와 「그 결과」가 서로 다른 것**이기 때문이다.
합쳐 두면 재시도가 새 명령처럼 보이고, 늦게 도착한 결과가 새 결과처럼 보인다.

### lease 기반 워커 — 죽은 워커를 회수한다

워커는 1초마다 자기 taskType 만 claim 한다. claim 하면 `TaskAttempt` 가 랜덤 `claimToken`
과 `leaseExpiresAt` 을 받는다. 완료하려면 **토큰 일치 + RUNNING + lease 미만료 + deadline
미도과** 를 전부 통과해야 한다 (`TaskAttempt.java:30`).

워커가 죽으면 lease 가 만료되고, 5초 주기 `recover()` 가 그 attempt 를 `TIMED_OUT` 시킨 뒤
**시도 한도가 남았으면 TaskRun 을 QUEUED 로 되돌린다** (`TaskRunService.java:251-269`).

### 멱등키 — 두 번 눌러도 한 번만 돈다

```
idempotencyScope(type, subjectType, subjectId) = "TYPE:SUBJECT_TYPE:SUBJECT_ID"
```

> **한 자리에서만 만든다** — 재생을 찾는 쪽과 만드는 쪽이 각자 문자열을 조립하면
> 조용히 어긋나고, 그러면 **같은 명령이 두 번 실행된다.**
> — `TaskRunService.java:40-42` 주석 원문

같은 키로 다시 오면 `inputHash` 를 비교해서 **같으면 새 실행 없이 기존 것을 돌려주고**,
다르면 `IDEMPOTENCY_CONFLICT` 409 로 거절한다. 여기에 더해 같은 입력으로 이미 도는 실행이
있으면 `TASK_ALREADY_RUNNING` 409 다 (`TaskRunService.java:63-73`).

〔슬라이드 힌트〕 좌: 3단 구조 + 상태 전이도 / 우: 멱등 판정 분기(같은 키·같은 해시 / 같은 키·다른 해시 / 동시 실행)

## A-3. 단일 AI 계약 — 엔드포인트 하나로 27종을 태운다

```
POST /internal/v1/ai/executions
```

taskType 27종이 **전부 이 하나**를 지난다 (`ai/app/api/executions.py:19,21-49`).
백엔드 enum 은 29종인데 차이 2개(`IDEA_ATTACHMENT_PARSE`, `CONCEPT_FACTORY_RUN`)는
AI 로 가지 않는 백엔드 전용이다.

> ⚠ `TaskType.java:2-5` 주석: **enum 본문에 주석을 쓰지 마라.**
> `ai/tests/test_internal_task_type_alignment.py` 가 enum 본문을 콤마로 쪼개 이름을 뽑아
> 두 목록의 일치를 테스트한다 — 본문 주석은 값 이름에 그대로 달라붙는다.

### 진입 게이트 8개 — 전부 통과해야 실행된다

| # | 검사 | 실패 시 |
|---|---|---|
| 1-2 | `Authorization` 토큰 | 401 |
| 3 | `X-Correlation-Id` ≠ body | 400 |
| 4-5 | contractVersion · taskSchemaVersion ≠ "1.0" | 422 |
| 6 | taskType 미등록 | 422 |
| 7 | deadlineAt 이 이미 지남 | **504 (retryable)** |
| 8 | **canonicalInputHash 불일치** | 400 |

앞단 미들웨어가 본문 2 MiB 초과와 **JSON 중복 키**를 먼저 막는다 (`ai/main.py:20,51-62`).

### `canonicalInputHash` — 같은 입력을 세 번 확인한다

백엔드와 AI 가 **같은 규칙**으로 SHA-256 을 만든다. 객체 키는 NFC 정규화 후 코드포인트 순
정렬, 숫자는 `BigDecimal.stripTrailingZeros()` (`CanonicalInputHasher.java:41-46,73-97`).

1. TaskRun 생성 시 서버가 재계산 → 불일치면 400
2. AI 수신 시 재계산 → 불일치면 400
3. **결과 채택 시** `run.inputHash == response.canonicalInputHash` → 불일치면 502 + 결과 REJECTED 저장

### AI 가 「재시도 가능」이라고 거짓말할 수 없다

응답의 `(code, reason, retryable)` 삼중을 백엔드가 대조한다. code 12종 각각에 허용 reason
집합이 있고, **`retryable` 은 reason 으로 결정된다** — AI 가 보낸 `retryable` 값이
`RETRYABLE_REASONS` 판정과 다르면 그 자체가 계약 위반이다
(`InternalAiExecutionClient.java:50-108,308-310`).

〔슬라이드 힌트〕 좌: 게이트 8개 세로 흐름 / 우: 해시 3중 검증 + retryable 대조

## 모듈 1. 컨셉 포트폴리오 — ② 법률: 조문을 만들 수 없게 잠근다

> 「법령명이나 조문을 만들지 말고 **제공된 routeId만 사용**한다. APPLIES/POSSIBLE 판단의

## 모듈 2. 사업 검증 — ② 근거 원장을 만드는 법

### A1 → A2 → A3 → A4 → B → C, **LLM 은 앞쪽 3곳뿐**

## 모듈 3. 기술·운영 / 재무 — ① 개요

### ① 무엇을 해 주는가

| | 입력 | 산출물 |
|---|---|---|
| 기술·운영 | 필수 사실 **7개** + AI 제안 **3개** 확정 + 근거자료 5종(선택) | 상용화 조언 7 · 파일럿 계획 · 운영비 계측 · 준비도 · 출시 게이트 |
| 재무 | 필수 **11개**(+수익모델별 최대 14) | 36개월 손익 · 손익분기 · 회수 · 민감도 · Monte Carlo · AI 서술 |

재무는 입력 경로가 **3가지**다 — 직접 입력 / **Word 템플릿 다운로드→작성→업로드** / AI 추정.

### ② 어떻게 하는가 — **계산은 코드가, 서술만 AI 가**

이 모듈의 설계가 한 줄로 요약된다: **AI 는 숫자를 만들지 않는다.**

```
① 결정론 계산   CAC · 월별 손익 · 손익분기 · 회수 · 민감도 14점
② Monte Carlo   2,000회 · 시드 20260810L 고정
③ AI 서술       ①②의 결과를 «통째로» 넘기고 해석만 시킨다
```

주요 수식 (`FinancialCalculationService.java:43-63`):

```
CAC              = (마케팅비 + 영업비) / 신규고객수
oneTimeRevenue   = 판매량 × 단가 × 성장배수
contribution     = 매출 − 변동비
breakEvenUnits   = 고정비 / 단위마진        (CEILING)
paybackMonth     = 누적현금흐름이 처음 0 이상이 되는 달
법인세            = 과세소득 × 20%
```

`unitMargin <= 0` 이면 **계산을 포기하고 사유를 남긴다** — `CONTRIBUTION_MARGIN_NON_POSITIVE`.
억지로 숫자를 만들지 않는다.

Monte Carlo 클래스 주석:
> `/** Repeats perturbed base cases; it is risk simulation, not an AI prediction. */`
> — `FinancialMonteCarloService.java:13`

**AI 가 실패해도 계산은 살아남는다.** `SYSTEM_CALCULATION_FALLBACK` 으로 결정론 결과가
그대로 저장된다 (`FinancialAnalysisService.java:143-152`).

### ③ 왜 안 지어내는가

**프롬프트로 부탁하지 않고 코드가 깎는다.** AI 재무 추정에는 가격 P 대비 비율 상한이 걸려 있다:

```python
caps = {"unitVariableCost": 0.45, "paymentFee": 0.05, "partnerPayout": 0.30,
        "customerIncrementalInfraCost": 0.20, "shippingCost": 1.00}
conservative_amount = max(1, math.floor(price * cap_ratio * 0.8))
```
— `finance_estimate/service.py:99-133`

상한을 넘으면 값을 깎고 「가격 가설 대비 단위원가 상한을 적용한 보수적 추정입니다」를
가정 목록에 **추가**한다. 프롬프트에는 단위 혼동 금지도 못박혀 있다:
> 「Never write 2,376,000 KRW in prose while returning 2,376 KRW.」 — `:52`

**기술·운영 자문은 근거 ID 를 검산한다.** 모든 조언·게이트·비용의 `basisIds` 는

**일반론을 거부하는 목록이 코드에 있다** (`tech_ops_advisor/service.py:127-143`):

> 「Never use a runId, generatedAt, stage status, seconds, llmCalls, or other execution

## 모듈 4. 시장 인터뷰 — ① 트윈 패널이란 무엇인가

## 모듈 4. 시장 인터뷰 — ② 지어내지 못하게 만든 장치

### 계약이 «스키마» 가 아니라 «경계» 를 지킨다

`MarketInterviewContract.java:14-37` 원문:
> 1. `caveats` 는 **비어 있으면 안 된다.** 빈 배열은 「경계가 없다」가 아니라 「경계를 떨어뜨렸다」다.
> 2. **백분율 칸이 없다.** 이 조사가 내는 수치는 `mentionCount`(사람 수)뿐이다.
>    **비율 칸을 계약에 열어 두면 언젠가 채워지고, 채워지는 순간 이 조사가 답하지 못하는 것을
>    답한 것이 된다.**
> 3. `mentionCount` 는 **표본을 넘을 수 없다.**

2026-08-13 에 검사 둘이 늘었다:
> 4. `mentionCount` 는 `respondentIds` 의 **길이와 정확히 같아야 한다.**
>    **AI 가 센 수를 받지 않는다 — 명단이 근거다.**
> 5. `alternatives` 합계가 답한 사람 수를 넘을 수 없다. 넘는다는 것은 **코딩이 사람을 복제했다**는 뜻이다.

### 주제 코딩 — LLM 은 이름표만 붙인다

> 「**LLM 은 이름표만 붙인다. 숫자와 인용문은 코드가 만든다.**

> 「대표 인용문을 써라」고 하면 **아무도 하지 않은 말이 결과에 실린다.**」 — `coding.py:1-6`

### 두 번 당하고 두 번 고쳤다

**1차 (2026-08-12) — 40명 조사에서 모든 주제가 40/40**
> 「대안 3개("가끔 요리한다"·"간편식·배달"·"참는다")가 **동시에 40/40** 이었다 —
> 한 사람이 셋을 다 한다는 뜻이라 응답 분포로는 성립할 수 없다.」

| 판 | 결과 |
|---|---|

| 2 | BARRIER 31 · CONCERN 25 |
| 3 | LIKE **40/40** · USAGE_SCENE **40/40** |

> 「응답 원문은 셋 다 같았고 완전중복 0건 · 40명 전원이 공유하는 어절 0개였다.
> 즉 **갈리는 것은 응답이 아니라 코딩이다.**」

② 카피 검증  ← 금지 표현·필수 고지 검사

## 모듈 5. 마케팅 — ② 근거를 못 만들게 스키마를 닫는다

전략이 인용할 수 있는 근거를 **런타임에 enum 으로 닫는다.**

```python
schema["properties"]["evidenceRefs"]["items"] = {"type": "string", "enum": allowed_refs}
```
— `ai/app/tasks/marketing_strategy/service.py:79-83`

**모델이 존재하지 않는 근거를 문법적으로 만들 수 없다.** 프롬프트로 「지어내지 마라」고
부탁하는 것이 아니라 스키마가 허용하지 않는다.

그래도 어긋나면: 같은 `TYPE` 의 후보가 **정확히 1개일 때만** 교정하고, 아니면
`AI_EVIDENCE_REFERENCE_INVALID` 502 로 실패시킨다 (`:21-57`). 2개 이상이면 어느 것인지
알 수 없으므로 **추측해서 고르지 않는다.**

〔슬라이드 힌트〕 좌: enum 으로 닫은 스키마 코드 / 우: 교정 규칙 분기(1개면 교정 · 2개 이상이면 실패)

## 모듈 6. 최종 사업 제안서 — ① 개요

### ① 무엇을 해 주는가

- **입력**: 포함할 선택 소스 체크박스 + `Idempotency-Key`
- **산출물**: 제안서 스냅샷(버전 관리) + **AI 검토 의견**(자동 후속) + PDF/DOCX
- 문서 구성: 표지+결재란 → 목차 → 의사결정 요약 → N개 절 → 부록 → (선택) AI 검토 부록

### ② 어떻게 하는가 — LLM 2회 (본문 1 + 검토 1)

```
POST /generate
 ├ 소스 수집 (필수 3 + 선택 8)
 ├ 근거 카탈로그 생성   ← 백엔드가 만든다. 소스당 최대 80항목, 각각 EV-<24hex>
 ├ TaskRun (maxAttempts=2)
 ├ AI 본문 생성                                   ← LLM 1회
 ├ 근거 정규화 + 해시 재확인 + 스냅샷 저장
 └ 검토 TaskRun 자동 큐잉 → AI 검토              ← LLM 1회
```

검토는 사용자가 누르는 게 아니라 **성공 시 자동으로 붙는다**
(`FinalBusinessProposalWorker.java:89-96`).

### ③ 왜 안 지어내는가 — 근거 인용 강제

이 모듈의 핵심이다. **인용할 근거를 AI 가 고르는 게 아니라 백엔드가 목록을 준다.**

1. **백엔드가 근거 카탈로그를 만든다** — 화이트리스트 루트 키 48개에서 추출,
   `evidenceKey = "EV-" + SHA256(type|id|path|value)[:24]`
2. **AI 스키마를 런타임에 닫는다** — `evidenceKeys.items.enum = allowed_keys`
3. **결과 재검증** — 5개 그룹의 type·key 를 전부 대조, 위반 시 502
4. **백엔드 정규화** — AI 가 쓴 key 를 카탈로그에서 찾아 **원문 사본으로 치환**

> 화면·PDF 의 「근거 상세」는 **AI 가 쓴 문장이 아니라 백엔드가 소스에서 뽑아 붙인 원문**이다.

같은 타입이 매니페스트에 2번 이상 나오면 **모호하므로 그 타입 자체를 제거**한다
(`FinalReportService.java:665-667`) — 애매하면 인용을 성립시키지 않는다.

`MARKET_INTERVIEW` 근거에는 자동으로 한계 문구가 붙는다:
> 「가상 정성 탐색이며 실제 고객 조사나 모집단 결과가 아닙니다」
> — `BusinessProposalEvidenceCatalog.java:110-111`

### ④ 숫자·계약

- 절 **8~10개**(스키마 강제) · 근거 소스당 최대 **80** · 카탈로그 전체 최대 **1000**
- `maxAttempts=2` · 생성 lease 8분/timeout 6분 · 검토 lease 6분/timeout 5분
- `evidenceKey` 패턴 `^EV-[0-9a-f]{24}$` · `sourceManifest` 3~30개
- 프롬프트 절대 규칙 **14개** (`prompts.py:4-25`)

〔슬라이드 힌트〕 좌: 근거 카탈로그 → enum 닫기 → 정규화 4단계 흐름 / 우: 「근거 상세는 AI 문장이 아니다」 비교

## B-2. 품질 — 계약을 «닫는» 방식

전 층이 같은 기법을 쓴다: **필드가 하나라도 빠지거나 남으면 거부**.

```java
Set.copyOf(node.propertyNames()).equals(EXPECTED_FIELDS)
```

```python
class StrictModel(BaseModel):
    model_config = ConfigDict(extra="forbid")
```

`extra="forbid"` 선언 **27곳 / 26개 파일**. 이것이 중요한 이유 3가지:

1. **양쪽 닫힌 스키마의 짝.** 백엔드가 닫혀 있는데 AI 가 열려 있으면
   「AI 는 통과했는데 백엔드가 거부」라는 비대칭이 생긴다.
2. **명시적 오류로 승격.** `extra_forbidden` → reason `UNKNOWN_FIELD` (`ai/main.py:34-35`).
3. **OpenAI structured output 의 `strict: true` 요건.** `additionalProperties: false` 가
   나와야 프로바이더가 스키마를 받는다.

### LLM 을 부르기 «전에» 스키마를 검사한다

`lint_provider_schema()` 가 5가지를 거부한다 — `unconstrained-object` ·
`additionalProperties` 가 false 아님 · `untyped` · `unbounded-array` · `unbounded-string`.
하나라도 걸리면 **호출 전에** 502 로 끊는다 (`marketing_content/models.py:159-193`).

〔슬라이드 힌트〕 좌: 닫힌 집합 비교 코드 2개(Java/Python) / 우: 린터 거부 조건 5가지

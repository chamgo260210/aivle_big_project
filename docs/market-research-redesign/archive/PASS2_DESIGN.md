# 2패스 설계 — 「절에서 출발해 쓰기」

## 왜 — 지금이 원본보다 못하다

| | 원본 `market-report.html` | 지금 `read_sections.py` |
|---|---|---|
| 재료 | 112건 · 1,395,167자 | **같음** |
| 문서당 상한 | 60,000자 | **같음** |
| 한 번에 보는 문서 | **약 30건** | **1건** |
| 지시 | **「보고서를 써라」** | 「9절 중 뭘 채우나, 최대 20개」 |
| 찬 칸 | 9칸 중 **7칸** | 9칸 중 **4칸** |
| 사실 | 약 75개 | 69개 (원본과 겹치는 것 **10개**) |
| 해석 문장 | 있음 | **없음** |

**재료도 상한도 같은데 못하다.** 원본에서 베낀 것은 질문 문구뿐이고, **그릇(문서 하나씩 · 개수 상한 ·
쓰지 않음)은 옛 슬롯 방식 그대로 뒀다.** 자세한 복원은 `THE_CASE.md`.

## 목표

**원본의 사실 75개를 체크리스트로 삼는다.** 지금 자동 산출은 그중 **10개**를 낸다.
이 수가 오르는지로 잰다. **원본을 넘지 못하면 이 설계는 실패다.**

---

## 설계

### 1패스 — 색인 (있는 것을 격하)

`tools/read_sections.py` 를 그대로 쓰되 **역할을 바꾼다.**
지금은 산출이지만, 앞으로는 **「2패스가 어느 문서를 열지 고르는 색인」**이다.

- 산출 중 쓰는 것: 문서 → 절 라우팅 (`section` 집합)
- 산출 중 안 쓰는 것: 사실 튜플 (증거로만 남기고 봉투에 안 보낸다)
- 이번 실험은 **기존 `p39-secFULL/sections.json` 을 재사용** → 1패스 비용 0

### 2패스 — 절별 집필 (신설 · `tools/write_sections.py`)

절 7개(`MARKET_SIZE` … `REGULATION`) 각각에 대해:

```
1. 그 절로 라우팅된 문서를 모은다
2. 180,000자 덩어리로 묶는다        ← 모델 창(gpt-4o-mini 128k토큰 ≈ 197,000자) 안
3. 덩어리마다 한 번씩:
     "이 절을 쓰는 데 필요한 사실을 **개수 제한 없이 전부** 뽑고,
      그 사실들로 **이 절의 문단을 써라**"
4. 덩어리가 둘 이상이면 **병합 호출 1회** — 덩어리별 산출을 받아 절 하나로 합친다
```

**⚠ 원본과의 차이를 여기서 인정한다.** 원본은 **380,000자 덩어리**를 한 번에 읽었다 —
큰 창을 가진 일반 에이전트였기 때문이다. gpt-4o-mini 는 그 절반이라 **덩어리를 쪼개고 병합**한다.
병합이 원본의 「한 번에 30건」을 얼마나 재현하는지는 **미지수이고, 이 설계의 최대 위험이다.**

절별 실측 (`p39-secFULL` 색인 기준):

| 절 | 관련 문서 | 글자 | 덩어리 |
|---|---|---|---|
| MARKET_SIZE | 41 | 885,523 | 5 |
| DEMAND | 43 | 879,917 | 5 |
| PRICE | 30 | 401,223 | 3 |
| REGULATION | 10 | 342,231 | 2 |
| COMPETITOR | 11 | 306,396 | 2 |
| UNIT_ECONOMICS | 15 | 305,470 | 2 |
| CHANNEL | 4 | 110,398 | 1 |
| **합** | | **3,231,158** (1패스의 2.3배) | **20** |

호출 20 + 병합 7 = **27회.** 입력 323만 자 ≈ 209만 토큰 → **약 490원.**

### 산출 모양

```json
{ "section": "PRICE",
  "facts": [ { "id":"f1", "quote":"…", "number_raw":"6,513", "unit_raw":"원",
               "year":"2025", "subject":"오뚜기 냉동식품 개당 평균 판매단가",
               "table_context":"…", "doc":"trace_id" } ],
  "body":  [ { "text":"8,900원은 같은 카테고리 평균단가의 1.37배다.",
               "cites":["f1"], "kind":"해석" } ] }
```

- **`body` 의 문장마다 `cites` 를 강제한다.** 근거 없는 문장을 못 쓰게 하는 유일한 장치다
- **컨셉 값(1팩 8,900원 · 예산 30억 · 채널 계획)을 프롬프트에 넣는다.**
  원본 값어치의 절반이 「8,900원은 6,513원의 1.37배」 같은 **비교**였고, 그건 컨셉을 알아야 나온다

### 게재 5겹은 그대로 쓴다 — 다만 **문장까지 내린다**

`tools/publish_gate.py` 를 `facts[]` 에 건다. 그리고:

> **떨어진 fact 를 인용한 문장은 같이 내린다.** 사유를 남긴다.
> 문단이 듬성해지는 것은 감수한다 — **근거가 떨어진 문장이 남는 것보다 낫다.**

원본은 이 검증을 **안 거쳤다**(스스로 명시). 그 대가로 인용 73건이 그 값의 근거가 아니었고,
게임회사·병원 자료 163건이 섞여 있었다. **베낄 것은 읽는 모양이지 검증 부재가 아니다.**

### 9절 `VERDICT` · 8절 `NOT_FOUND`

7절 산출을 받아 **1회.** 「사업안을 지지하는 것 / 흔드는 것」을 쓴다(원본 9절과 같은 모양).
`NOT_FOUND` 는 절이 빈 이유 + 처방 3분류(직접 입력 / 시장 인터뷰 / 공개 자료에 없음).

## 아직 안 정한 것 — 이 설계의 구멍

1. **어느 절에도 안 걸린 문서 42건을 버리는가.**
   1패스에서 `not_found` 였다. 2패스가 색인만 보면 이 42건은 **영영 안 읽힌다** —
   0순위 철학(「문서는 하나도 안 버린다」) 위반으로 읽힐 수 있다.
   대안: (a) 그대로 버린다 (1패스가 이미 봤으므로) (b) 미분류 덩어리로 만들어 한 번 더 읽힌다
2. **병합이 원본의 「한 번에 30건」을 재현하는가.** 덩어리 5개를 따로 읽고 합치면
   덩어리를 가로지르는 비교(「A문서의 6,513원 vs B문서의 8,900원」)가 나오는가.
3. **게재 게이트가 문장을 내리면 문단이 무너지는가.** 절당 사실이 절반 떨어지면
   문단이 말이 안 될 수 있다. 다시 쓰게 할 것인가(추가 호출), 그냥 둘 것인가.
4. **비용 490원.** 유료이므로 착수 전 사람 승인.
5. **원본을 넘는다는 보장이 없다.** 원본은 큰 창의 일반 에이전트가 읽었다.
   덩어리+병합으로 그것을 대신할 수 있는지는 **돌려 봐야 안다.**

## 정지 규칙 (사전 등록)

**지표 1개** — `market-report.html` 사실 75개 체크리스트 적중 수. 지금 **10개**.
**예측** — 2패스 뒤 **30개 이상**.
**정지** — 20개 미만이면 이 설계를 버리고 「큰 창 모델로 원본을 그대로 재현」을 검토한다.

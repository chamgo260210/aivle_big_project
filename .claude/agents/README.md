## 왜 이렇게 짰나

이 저장소에서 병렬화의 이득은 **조사·검증**에 있고, 위험은 **구현**에 있다.
두 곳(또는 세 곳)을 동시에 고쳐야 하는 짝이 여럿이라, 서로 모르는 에이전트가 한쪽씩 고치면
**컴파일도 테스트도 통과한 뒤 런타임에만 깨지거나 결과가 조용히 버려진다.**

그래서:
- **조사는 병렬** (읽기 전용이라 안전)
- **구현은 순차**, 그리고 **계약 짝은 한 에이전트가 양쪽을 다 고친다**
- 구현 뒤에 **계약 감사**를 반드시 통과시킨다 — 쪼개짐을 잡는 유일한 자리
- **유료 실행(실제 LLM 호출)은 어떤 에이전트도 스스로 안 돌린다.** 보고하고 멈춘다

## 쓰는 법

### 워크플로로 한 판씩 (권장)

```
Workflow: { name: "business-validation", args: "1-1 칸→근거 매핑을 기계가 확정" }
```

조사(병렬 2) → 분배 → 구현(순차) → 계약 감사 → 검증 → 수선(최대 2회).
에이전트 약 8~10개.

⚠ 워크플로는 **명시적 요청이 있어야** 돌아간다. 세션에서 "워크플로로 돌려줘"라고 하거나
`ultracode` 를 쓴다.
